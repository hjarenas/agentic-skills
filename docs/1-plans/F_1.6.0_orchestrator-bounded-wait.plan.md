# Orchestrator Bounded Wait Implementation Plan

## Overview

TRIP orchestrators have no written contract for what to do when a dispatched worker never reports
back. This plan adds one: a bounded-wait rule in the shared agent routing contract, a
merge-slot-specific recovery rule in the phase-scheduling reference, report-integrity completion
tags for the two roles that lack them (`discovery`, `planner`), and the wiki pages that describe
the resulting orchestrator↔worker relationship. The change is purely additive prose in the `trip`
plugin plus its architecture wiki pages — no scripts, no behavioural code, no restructuring of the
phase-skill topology.

## Problem Statement

An orchestrator dispatched a `planner` child. The child completed and its work landed on disk, but
its report back to the parent failed in transport ("the peer session is no longer reachable") and
surfaced in the grandparent's conversation instead. The parent never received a completion signal
and entered an unbounded busy-wait: poll → spawn a 310s Monitor → timer tick → poll, 49 Monitors
deep, roughly 370k tokens for that flow against 65k and 74k for two sibling flows that finished
normally. The work had been done for 25 minutes. Nothing in the system detected the contradiction
between "the child has exited" and "the parent is still waiting".

The root cause is an instruction vacuum, not a wrong instruction. A grep of `plugins/trip/**/*.md`
for `monitor|poll|wait|busy|background|liveness|timeout|deadline` returns three hits, none of them
a wait instruction (`TRIP-1-plan/SKILL.md:67` "deadlines" inside a question prompt;
`TRIP-hotfix/SKILL.md:28` "cannot wait for"; `TRIP-auto/SKILL.md:17` the child-orchestrator line).
The busy-wait was emergent behaviour filling that vacuum. **The fix is therefore additive: the
contract must be written, because there is nothing to correct.**

Two concrete consequences of the vacuum:

1. **Every tag-parsing site is an unconditional "wait for tag T"** with no branch for "no report
   ever arrives": `TRIP-1-plan/SKILL.md:117`; `TRIP-2-implement/SKILL.md:123-125`, `:135`,
   `:141-142`, `:144`, `:246`; `TRIP-2-implement/phase-scheduling.md:57-64`, `:80-86`.
2. **The serialized merge slot is a deadlock by construction.** In
   `TRIP-2-implement/phase-scheduling.md:50-64`, one phase holds the merge slot from the moment its
   merge/cleanup begins until that same phase's terminal `WORKSPACE_COMPLETE`. A phase whose worker
   dies mid-merge never emits that tag, so the slot is never released and *every other phase* in
   the parallel flow stalls behind it — a strictly worse outcome than the single-worker case.

Nothing in the plugin mentions cross-session messaging or peer reachability at all, so the
transport that failed is not modeled anywhere in the contract.

**Corrected framing (superseding the incident-only reading above).** Production evidence gathered
after this plan was approved sharpens the diagnosis, and the text below governs where it differs
from the single-incident narrative:

- The failure mode is **not** workers dying. It is workers and child orchestrators **returning
  early or stopping** when a message they are waiting on never arrives. Sometimes they spin first
  (the ~370k-token incident); often they simply end their turn with no report at all.
- **Lost child→parent reports are common, not exceptional** — roughly **one delivery in three**
  failed across a single observed live session. Reconstruction from on-disk artifacts is therefore
  a **normal path** in this contract and must not be written as an emergency procedure.
- **Work is never lost** when this happens; it sits in the phase worktrees. The observed cheap,
  repeatable recovery is `ListAgents` to spot a stalled parent, then a **direct `SendMessage` to
  the stopped child orchestrator to resume it from its transcript** — not a re-dispatch and not a
  re-run of the assignment.
- **The top-level agent has become a message bus.** Orphaned reports ("the peer session is no
  longer reachable, so reporting here instead") arrive in a grandparent's conversation while the
  rightful parent blocks waiting for exactly that verdict; relaying it unblocks the parent
  immediately. Observed at least twice (a `planner` report, and a `batch-reviewer`'s
  `BATCH_APPROVED`). Nothing in the plugin tells any agent to relay.
- **A stopped agent executes no prose.** Every rule in `agent-routing.md` addressed to a *waiting*
  orchestrator is unreachable by an orchestrator that has already stopped. That case is
  addressable only from **outside**, by whoever dispatched it — so the contract needs a
  dispatcher-side rule, not only a waiter-side one.

## Solution Architecture

Three layers, in decreasing generality:

1. **A shared bounded-wait contract in `plugins/trip/references/agent-routing.md`.** This file is
   already read by `TRIP-1-plan:13`, `TRIP-2-implement:25`, `TRIP-3-release:15`, `TRIP-auto:14`,
   `TRIP-hotfix:14`, every `plugins/trip/agents/*.md`, `README.md:68` and
   `docs/archi/pages/trip-plugin.md:8-10`. One edit there reaches every orchestrator — the same
   de-duplication move as commit `f311a62`. Every wait surface needs this text, so it is inlined
   there rather than pushed behind a pointer.
2. **Merge-slot recovery semantics in `plugins/trip/skills/TRIP-2-implement/phase-scheduling.md`.**
   Branch-specific: only the phase-parallel flow has a shared slot whose loss strands siblings. It
   lives with the mechanism it modifies, which only the phase-scheduling branch reads.
3. **Report-integrity completion tags for `discovery` and `planner`**, in both owning locations
   (the agent file and the Roles table in `agent-routing.md`).

Design stance, reflecting the binding decisions taken before planning:

- **The orchestration layers stay.** `TRIP-auto` continues to invoke `TRIP-1-plan`,
  `TRIP-2-implement` and `TRIP-3-release` as child orchestrators. The nesting is not the defect;
  the missing contract is. No change to the phase-skill topology.
- **Tags are hygiene, not the liveness fix.** A completion tag catches a report that *arrived but
  trailed off*. A worker that vanished emits nothing either way, tag or no tag. The plan must say
  this explicitly wherever the tags are introduced so no future reader mistakes tags for the
  bounded-wait mechanism.
- **Bounded iteration is an existing repo idiom; reuse its vocabulary.** `TRIP-1-plan:123`,
  `TRIP-2-implement:258`, `TRIP-auto:50` and `:59` all read "Cap at 5 rounds… surface remaining
  findings and let the user decide", and `phase-scheduling.md:83-86` reads "surface
  `WORKSPACE_BLOCKED` to the user instead of retrying indefinitely". The new contract mirrors that
  shape — a cap, then stop and surface — rather than inventing new vocabulary.

### Why not other approaches

- *Flattening the orchestrator layers* would remove one nesting level but leave the same unbounded
  wait at every remaining dispatch boundary, at the cost of a large restructure. Explicitly ruled
  out by the user.
- *A polling/heartbeat protocol* is what caused the incident. The contract must forbid polling the
  child, not formalize it.
- *A harness-level "await child" primitive* does not exist. `Monitor`, `SendMessage`, `TaskStop`,
  `ListAgents` and `TaskOutput` were the primitives observed available; none of them is "await
  child N" or "is child N alive" except `ListAgents`, which enumerates agents and their status.

## Implementation Details

### 1. Bounded-wait contract — shared, all orchestrators

**File**: `plugins/trip/references/agent-routing.md` (modify)

**Current state**: 183 lines. Sections: Orchestrator boundary, Roles, Routing configuration (with
the Codex bridge role mapping and Codex-heavy preset), Dispatch contract. The only text adjacent to
this problem is `:14` ("stop, retry, or reroute a **failed** assignment" — a failed assignment, not
a silent one), `:24-25` ("If no suitable worker can be launched, stop and report the missing
capability"), and `:171-173` (a backgrounded Bash run "cannot wake the worker that dispatched it —
the turn ends with no result, not a slow one", scoped narrowly to long test commands). None of
these covers a dispatched worker that simply never reports.

**Modifications**:

- Add a new top-level section — proposed heading **"Waiting for a worker"** — placed immediately
  after the existing `## Dispatch contract` section, so a reader arrives at it right after learning
  what a dispatch must contain. It must state, in prose an orchestrator will actually follow:
  - **What counts as waiting.** Any turn whose only purpose is to discover whether a dispatched
    worker has reported: re-reading the same status, re-listing agents, scheduling a timer, or
    taking any no-op turn to "check again". A turn spent doing genuinely different routing work is
    not a wait.
  - **The cap, and the cadence that makes the cap meaningful.** The harness exposes **no blocking
    "await child" primitive** (see "Why not other approaches"), but it does expose a **bounded,
    duration-bearing passive wait**: the `Monitor` tool accepts a timeout, and the incident
    transcript itself shows it being spawned repeatedly with a 310-second timeout. That primitive
    is the required mechanism for the elapsed cadence below. The contract therefore does **not**
    ban timers — the incident's defect was an *unbounded* poll loop with no exit, not the existence
    of a timer. It bounds waits on two axes **that both apply**, and a wait ends when **either**
    ceiling is reached:
    - **Count ceiling:** at most **3** check turns per dispatched worker, in the existing
      "Cap at N… then surface" idiom, deliberately below the review loops' 5 because unlike a
      review loop each additional check produces no new work.
    - **Elapsed ceiling:** a total wall-clock budget per dispatch, and a **minimum spacing** before
      any check turn may be spent, so the three checks cannot be consumed back-to-back while a
      healthy worker is still executing. Recommended: minimum spacing **5 minutes**, total budget
      **20 minutes**. A check turn taken before the minimum spacing has elapsed does not count as
      one of the three and must not be taken at all.
    - Escalating timer intervals are not a substitute for either ceiling, and neither ceiling may
      be reset by a partial signal, a sibling's progress, or a child orchestrator saying it is
      still working.
    - **Both ceilings are required; neither is optional.** A count-only cadence is not an
      acceptable outcome: three back-to-back checks against a healthy, still-working worker would
      exhaust the ceiling within seconds and stop routine work as "ambiguous", which is the same
      missing-elapsed-gate defect the incident exposed, merely inverted.
    - **Superseded — how the elapsed gate is actually executed.** An earlier version of this bullet
      told the implementer to write the cadence against "`Monitor`'s timeout". That premise is
      **wrong and must not be shipped**: `Monitor` is an asynchronous background watcher that
      requires a `command` or `ws`, streams stdout lines as notifications, and whose `timeout_ms`
      **kills the monitor rather than blocking the caller**. Arming it does not pause the
      orchestrator's turn, so "leave ~5 minutes between checks" has no execution path from that
      sentence alone. The working construction the text must name instead is **a duration-bearing
      background wait whose *command* exits when the interval elapses or the report lands, and
      whose exit notifies the orchestrator** — e.g. `Monitor` or a backgrounded `Bash` running an
      `until`-loop with a `sleep`. The implementer names the concrete construction it uses and
      confirms that construction runs in the orchestrator context. A count-only cadence remains
      unacceptable; if no such construction can be made to work, **stop and surface that this
      contract cannot be safely implemented as written** rather than inventing a mechanism or
      shipping the count ceiling alone. See Open Items.
  - **The prohibition on polling the child — narrowed (supersedes the earlier flat ban).** The
    banned act is **pinging a live, still-working worker to ask whether it is done**, and repeated
    or unbounded pinging of one, which is the token-burning defect the incident exposed. That stays
    banned. What is **not** banned — and what the text must make impossible to read as banned — is
    **resuming a child that has demonstrably stopped without delivering a report**. The
    discriminator is **observed child status** (stopped, or completed with no report delivered),
    never impatience or elapsed time alone. Absence of a report is still not evidence the worker is
    alive. A bounded, spaced passive wait is permitted; an unbounded one, or any wait that pings a
    live worker, is not.
  - **Dispatcher-side rule: what to do when a child stops without reporting.** A stopped agent
    executes no prose, so nothing written for a *waiting* orchestrator can recover it — only its
    dispatcher can. When a dispatcher observes (via `ListAgents`, or via a report that surfaced
    elsewhere) that a child it dispatched has stopped or completed without delivering its result,
    it must **resume that child with a single direct `SendMessage`** asking it to continue from its
    transcript and deliver its report. This is the observed working recovery; it is explicitly
    **not** a re-dispatch, **not** a re-run of the assignment, and **not** a ping of a live worker.
    One resume attempt per observation; if the resumed child stops again without reporting, fall
    through to the artifact-and-status check below and then stop and surface. Never re-dispatch the
    same assignment while its worktree artifacts stand — the work is in the worktree, not lost.
  - **Relay rule: a report addressed to someone else must be forwarded.** Because reports are
    frequently orphaned into a grandparent's or sibling's conversation, any agent that receives a
    report evidently intended for a different agent — it names another agent's assignment, or
    arrives with a "the peer session is no longer reachable" preamble — must **relay it to that
    agent with `SendMessage`** rather than only acting on it locally, and say in its own report
    that it relayed. The rightful parent is, by construction, blocked on exactly that message.
    Relaying is not polling: it delivers a result that already exists, it does not request one.
  - **Baseline at dispatch — a precondition, not an afterthought.** Most assignments *modify*
    artifacts that already exist, so "the file is there" proves nothing. Every dispatch must record,
    at the moment it is issued, an assignment-specific baseline for each named output: the path,
    plus a content hash (or the file's absence), plus the repository `HEAD` and porcelain status
    line relevant to it. The contract must state that a dispatch without a recorded baseline cannot
    later be reconstructed and must be stopped and surfaced instead of guessed at.
  - **What to check when the cap is hit**, in this order: (a) a **validated post-dispatch delta**
    against the recorded baseline — the named output's hash differs from the baseline hash (or the
    file now exists where it did not), and the change is of the shape the assignment asked for
    (the plan file gained the required sections; the tree gained the staged paths); and (b) the
    **child's status** via `ListAgents` where the current context can call it. State the
    contradiction rule plainly: *a child that shows as completed while the orchestrator is still
    waiting means the report was lost, not that the work is pending.* Only a **validated delta plus
    completed status** may be treated as a completed assignment; continue the flow from the artifact
    and record in the flow notes that the report was reconstructed rather than received. **Write
    this as a normal path, not an emergency procedure** — lost reports run around one in three, so
    an orchestrator should expect to reconstruct routinely and proceed without alarm or user
    escalation whenever the delta validates.
  - **No delta, no reconstruction.** An artifact byte-identical to its baseline, a delta that does
    not match the assignment's shape, or an unrecorded baseline is *not* evidence of completion,
    regardless of child status. Stop and surface. Proof of completion is observed, never inferred.
  - **An honest capability caveat (updated with production evidence).** `ListAgents` is
    **confirmed working from the top-level orchestrator context** — it is what detects the
    stalled-child signature in production. Its availability **inside nested child-orchestrator and
    worker contexts remains unconfirmed**. State both halves: where it is callable, the status
    check is available; where it is not, the on-disk artifact check is the whole test and an
    ambiguous result goes to the user rather than into another wait. Do not assert a capability the
    contract cannot guarantee. See Open Items below.
  - **What "stop and surface" looks like.** Stop the flow, do not retry the dispatch, and report to
    the user: which role and assignment, what evidence of completion was and was not found, where
    the partial artifacts are, and the two options (resume from the artifact, or re-dispatch). This
    mirrors `phase-scheduling.md:83-86`'s existing "surface … instead of retrying indefinitely".
  - **One sentence naming the transport.** Cross-session/peer messaging between a worker and the
    orchestrator that dispatched it can fail after the worker's work has landed; a missing report
    is therefore not proof of missing work. No file in the plugin currently says this.
- Add one cross-reference sentence in `## Orchestrator boundary` beside the existing `:14` bullet,
  extending "stop, retry, or reroute a failed assignment" to cover a *silent* one and pointing at
  the new section.

**Size justification (corrected — supersedes both the earlier ~25-45 line budget and the
~55-70-line amendment's arithmetic)**: the amendment's claim that a 55-70-line section put the file
at "~200-215 lines, still inside the 223-line de-facto ceiling" was **arithmetically false** and is
withdrawn. `agent-routing.md` carries **184 lines of content other than this section** (the file now
measures 254 lines with the section implemented at 70). The correct sum is **184 + 55-70 = 239-254**,
which is **above** 223, not below it. The section budget of **~55-70 lines** is retained; what
changes is the ceiling claim.

**The ceiling for this one file is deliberately raised to 255 lines.** Justification, stated plainly:
(a) 223 was never a documented limit — it is a de-facto observation of `TRIP-3-release`'s length, and
`TRIP-2-implement` already stands at **299 lines**, so 254 is not even the longest file in the plugin;
(b) `writing-for-agents/SKILL.md:39` says to inline what *every* branch needs and push behind a
pointer only what *some* branches reach — `agent-routing.md` is read by every orchestrator and every
worker on the path they actually take, so its length is not disclosure debt, it is the contract every
reader needs in front of them; (c) the split precedent in `f311a62` moved text that only some branches
reach, which is the opposite case — splitting the wait contract into a sibling reference would cost a
pointer hop on a path *every* orchestrator takes, and save no reader any tokens. A sibling reference
file therefore remains explicitly **not** proposed, and the file is **not** to be tightened purely to
chase 223.

This is an explicit, justified raise, **not** permission to drift: an implementer that exceeds ~70
section lines (i.e. takes the file past **255**) must surface to the planner rather than absorb the
overrun silently, and must **not** split the file unilaterally.

### 2. Merge-slot recovery — phase-parallel flow only

**File**: `plugins/trip/skills/TRIP-2-implement/phase-scheduling.md` (modify)

> Note: discovery reported this file as `plugins/trip/references/phase-scheduling.md`. It is
> actually at `plugins/trip/skills/TRIP-2-implement/phase-scheduling.md`; the line numbers cited
> throughout are correct for the real path.

**Current state**: 92 lines. `:50-64` "Merge/cleanup is serialized" defines the merge slot, held
from the start of a phase's merge/cleanup until that same phase's terminal `WORKSPACE_COMPLETE`.
`:66-89` "Merge conflict handling" keeps the slot held through the entire conflict-resolution
sub-flow and ends with "surface `WORKSPACE_BLOCKED` to the user instead of retrying indefinitely".
Both rules are called out at `:2-4` as rules that must not be relaxed. Neither covers a
slot-holding phase whose worker reports nothing at all.

**Modifications**:

- Extend the "Merge/cleanup is serialized" section with a **stuck-slot** rule: the bounded-wait
  contract from `agent-routing.md` applies to the slot-holding `workspace-worker` dispatch, and
  when its cap is hit the git state of the feature worktree — not the missing tag — is what
  determines whether the merge completed.
- **The orchestrator must not gather that evidence itself.** `agent-routing.md:19-21` forbids the
  orchestrator from running git commands, and this feature exists to protect exactly that boundary.
  The rule must instead prescribe a **recovery audit**: a *new*, **read-only** `workspace-worker`
  dispatch whose entire assignment is to report the observations listed below and change nothing —
  no merge, no commit, no push, no worktree removal, no branch deletion.
  - State explicitly why this is not a violation of the no-ping/no-re-dispatch rule: it is a new
    assignment to a **different** worker asking about **repository state**, not a message to the
    silent worker and not a retry of the lost assignment. The lost worker is never contacted.
  - The audit dispatch is itself subject to the bounded wait, at the same caps. If the audit also
    goes silent, stop and surface — do not audit the audit.
- Define the **observable, phase-specific test** the audit must report, so a merely-clean worktree
  with some commit pushed can never release the wrong phase's slot. All four must hold:
  1. no in-progress merge — `MERGE_HEAD` absent in the feature worktree (and no rebase/`CHERRY_PICK`
     state), working tree clean per porcelain;
  2. the feature branch `HEAD` is a **merge commit** (two or more parents) created by `--no-ff`;
  3. one of that merge commit's parents is the **expected tip of this specific phase's branch** —
     the phase branch commit the orchestrator recorded when it dispatched the merge (this is the
     phase-specific half of the baseline required by section 1);
  4. the observed remote feature ref (`git ls-remote`, not a possibly-stale local
     `refs/remotes/...`) equals that exact `HEAD` object id.
- Define the terminal outcomes explicitly, and state that the slot is released in none of them by
  inference alone:
  - **All four hold → "merge landed; slot releasable".** This is *not* the same claim as
    `WORKSPACE_COMPLETE`, which per `phase-scheduling.md:4` fires only after commit, push **and**
    cleanup. Introduce the narrower, named condition and use it here: release the merge slot,
    recompute the frontier, and record the reconstruction in the flow notes — while treating
    cleanup as **outstanding, not done**.
  - **Cleanup remainder has a named owner.** A report can be lost after push but before the phase
    worktree is removed or the phase branch deleted. When the audit reports "merge landed" but the
    phase worktree or branch still exists, the orchestrator dispatches a **separate, scoped
    cleanup** `workspace-worker` assignment (remove that phase worktree, delete that phase branch,
    nothing else) and requires its `WORKSPACE_COMPLETE`. Only after that does the phase count as
    fully `WORKSPACE_COMPLETE`. The slot is not held waiting for cleanup — cleanup touches only
    that phase's own worktree and branch — and this must be said, so the two conditions are not
    re-fused by a later reader.
  - **Any of the four fails, or the audit is ambiguous → stop** the whole phase-scheduling loop and
    surface to the user exactly as the recurring-conflict case at `:83-86` already does. Do **not**
    dispatch another merge/cleanup, and do **not** release the slot on a guess.
- **(added — ratified from a live observation during this flow)** Correct the branch-deletion verb
  at **all three** `git branch -d` sites in this file — normal merge step 3, the cleanup dispatch,
  and the conflict path. `-d` compares the phase branch against the **currently checked-out HEAD of
  the primary repo**, which is normally an unrelated branch, so it refuses with "not fully merged"
  even when the phase merged correctly. The authoritative merged-ness test is
  `git merge-base --is-ancestor <phase-tip> <feature-branch>`; once that passes, the delete must use
  `git branch -D`. Keep the rule at all three sites — two of them (normal merge step 3 and the
  cleanup dispatch) sit in the **normal** merge flow, not the recovery flow this phase was chartered
  for, and the rule is worthless if it only applies on the recovery path, because the same `-d`
  refusal occurs on every normal cleanup.
- State the blast radius in one sentence: a stuck slot strands every other phase, which is why this
  case gets an explicit rule rather than relying on the general contract alone.
- Preserve the two never-relax rules verbatim and extend the file's `:2-4` preamble to name the
  stuck-slot rule as a third, so a reader who only skims the preamble still sees it.

**Dependent text that must move in lockstep** (same phase as this edit — these describe the same
mechanism and will contradict it otherwise):

- `plugins/trip/skills/TRIP-2-implement/SKILL.md:67-77` — the "Phase Scheduling" summary that
  enumerates the never-relax rules; add the stuck-slot rule to that enumeration.
- `plugins/trip/skills/TRIP-auto/SKILL.md:119` — the Failure handling bullet describing the
  deliberate mid-merge stop; add the lost-report stop as a second named condition under which the
  worktree is left in place for a human.
- `docs/archi/pages/worktree-parallelism.md` §"Phase gate and serialized merge" (`:48`) and
  §"Failure handling" (`:70`) — describe the stuck-slot outcome and its two resolutions.

### Risk assessment

- **Rebase conflict on `plugin.json`** — *likely*. Commit `f816215` exists precisely because two
  branches collided on the `version` field. Bump the version in its own late phase, immediately
  before release, and expect to re-resolve it on rebase.
- **Checks consumed back-to-back** — *moderate, raised in review*. Three check turns with no
  spacing can all be spent within seconds of dispatch, declaring a healthy worker lost. Mitigated by
  the minimum-spacing rule and the elapsed budget in §1, both of which are required gates that must
  hold before a check turn may be taken — there is no count-only fallback that would reopen this
  risk, and an implementer unable to satisfy the elapsed gate stops and surfaces instead.
- **A cap that is too tight** — *moderate*. A legitimately slow worker whose report is merely late
  could be declared lost. Mitigated by making the artifact check, not the cap, the thing that
  decides the outcome: the cap only triggers an inspection, and an ambiguous inspection stops and
  asks the user rather than assuming either way.
- **Releasing the merge slot on a guess** — *high severity, low likelihood*. Wrongly concluding a
  merge completed and dispatching the next phase's merge into a mid-merge worktree would corrupt
  the feature branch. Mitigated by requiring the four-part, phase-specific merge test (§2) —
  observed via a read-only audit dispatch, and identifying *this* phase's merge commit rather than
  any commit — as the *only* slot-releasable condition, and stopping on anything else.
- **`ListAgents` unavailable in the context that needs it** — *unknown, tracked below*. Mitigated by
  the honest caveat in section 1 rather than by an assumption.
- **Prose that does not change behaviour** — *inherent*. `SKILL.md` content is not unit-testable;
  the only verification is invoking the skill live. See Test Impact.

### Edge cases the text must cover

- The report arrives *after* the orchestrator reconstructed completion from the artifact (accept it
  as confirmation, do not re-run the assignment, do not double-tick checkboxes).
- The artifact exists but is clearly partial (a plan missing required sections, a half-staged tree)
  — that is not completion; stop and surface.
- The very first dispatch of a flow has no prior artifact to compare against — the assignment's own
  named output path is the artifact to check.
- A worker whose assignment produces **no** on-disk artifact (a pure read-only report, e.g.
  `discovery` or `plan-reviewer` when the report is only spoken) — for these the child-status check
  is the only signal, and when `ListAgents` is unavailable the correct move is to stop and surface,
  never to wait longer.
- Nested waits: a parent waiting on a child orchestrator that is itself waiting on a worker. The
  cap applies independently at each level; the parent must not extend its cap because the child
  says it is still working.
- A child orchestrator that **stopped** (ended its turn silently) rather than one still running —
  resume it once via `SendMessage`, never re-dispatch its assignment on top of its worktree.
- A report for **another** agent arriving in this agent's conversation — relay it, then continue
  this agent's own work; do not silently consume it.
