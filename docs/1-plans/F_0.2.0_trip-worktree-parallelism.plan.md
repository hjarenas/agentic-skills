# TRIP Worktree Parallelism Implementation Plan

## Overview

Redesign the `trip` plugin so `TRIP-auto` flows can run in parallel (each isolated in its own
git worktree) and, within a single flow, independent implementation phases can also run in
parallel (each in its own worktree branched off the feature branch). Phases commit and merge
back individually as they clear a full-phase gate, and exactly one deep code review still runs
feature-wide after all phases land. A related `codex-bridge` bug — its code-review prompts diff
against the wrong baseline once a branch carries more than one commit — is fixed alongside, since
commit-per-phase makes the bug load-bearing rather than latent.

## Problem Statement

Today `TRIP-1-plan` commits one branch per whole flow (`git checkout -b feat/<slug>`) and
`TRIP-2-implement` runs one implementer/reviewer/tester loop, single-threaded, across all phases
in sequence, with zero commits until `TRIP-3-release`'s Step 9. This means:

- Two `TRIP-auto` runs in the same repo collide on the same working tree — only one flow can be
  "in progress" at a time.
- Within one flow, independent phases (e.g. a backend change and an unrelated docs update) are
  forced through a single sequential batch loop even when nothing about them depends on the
  other.
- `codex-code-review`'s `start.tpl`/`resume.tpl` hardcode `git diff HEAD`, which only shows the
  working tree against the *last commit*. That is harmless today (there are no intermediate
  commits before release), but is a live bug the moment any commit lands mid-flow: the diff would
  silently narrow to "since the last commit" instead of "the whole feature," and a reviewer would
  approve a change without ever having seen most of it.

## Solution Architecture

Two independent axes of parallelism, layered on git worktrees (not `EnterWorktree`/`ExitWorktree`
or Agent Teams, since TRIP workers must remain dispatchable to non-Claude-Code harnesses):

1. **Outer parallelism** — `TRIP-1-plan`'s persist step creates a dedicated worktree per flow
   (`../<repo>-<slug>-<suffix>`) instead of checking out a branch in place. Every worker dispatched
   for the rest of that flow (`TRIP-2-implement`, `TRIP-3-release`, and their workers) operates
   with that worktree as its working directory. Two flows never touch the same tree.

2. **Inner parallelism** — the plan's `### Phase N` headings gain a `Depends on:` line. During
   `TRIP-2-implement`, the orchestrator computes the **frontier** (phases whose dependencies are
   all merged), and dispatches one worktree-isolated batch loop per frontier phase in parallel,
   each in worktree `../<repo>-<slug>-<suffix>-phase-<n>`, on branch
   `feat/<slug>-<suffix>-phase-<n>` — flat, hyphen-joined, **not**
   `feat/<slug>-<suffix>/phase-<n>`: git stores branch refs as a path hierarchy under
   `.git/refs/heads/`, and `feat/<slug>-<suffix>` already exists as a ref (a file) once the
   feature branch is created, so a branch name nested under it is invalid and fails with `fatal:
   cannot lock ref ... exists; cannot create ...` — branched off the *feature* branch. A phase that
   clears its own full-phase gate (delta review + testing) is committed on its phase branch and
   merged (`--no-ff`) into the feature branch by `workspace-worker`; the frontier is then
   recomputed so newly-unblocked phases join. Exactly one deep, feature-wide code-review pass
   still runs once, after every phase has merged — it is the only pass positioned to catch
   cross-phase integration issues, so per-phase deep review would be redundant, not just slower.

Both axes reuse the existing worker roster and completion-tag contract; only `workspace-worker`
gains new authorized operations (`git worktree add/remove`, `git merge --no-ff`), documented as
prose in its allowlist mechanism — no new role, no new harness concept.

  disjoint files/subsystems — independent phases (different `Depends on: none` phases) may run

  presented to the user, the `plan-reviewer` (or the planner itself, self-checking, when review is

  phase's `Depends on:` chain back to a root; revisiting a phase already in the current chain is a

  going empty partway through, which is exactly the gap `TRIP-2-implement`'s own defensive stop
  has to backstop — so this check is this plan's first and cheapest line of defense against a
  silent hang, not a redundant one.

### 2. `plugins/trip/skills/TRIP-2-implement/SKILL.md`

**File**: `plugins/trip/skills/TRIP-2-implement/SKILL.md`

**Current state**: Step 0 (lines 31-44) checks out the single branch the plan created and
continues on it, in place — no worktree concept. The batching section (lines 48-118) runs one
implementer/reviewer/tester loop across all phases sequentially, "never span phase boundaries"
(line 64) but with no mechanism to run more than one phase's loop at a time. Step 5 (line 108)
says "No commits — history stays clean for release." "Final pass" (lines 113-118) is a
full-diff `batch-reviewer` pass over the whole working tree, run once after the last batch. The
Testing Gate (H2, lines 122-178) and Independent Code Review loop (H2, lines 181-231) already run
once, feature-wide, after all batches — this property is preserved, just re-scoped to run after
all *phases* are merged instead of after all *batches*.

**Modifications**:

- Rewrite Step 0 to find the worktree `TRIP-1-plan` already created by running `git worktree list`
  from the primary tree and matching the entry whose branch carries the plan file's commit —
  **not** by reconstructing a path from the plan's recorded branch/slug plus a guessed suffix. The
  collision-safe suffix is generated once, randomly, at persist time and is not recorded anywhere
  a future reader could reliably regenerate it from naming convention alone, so `git worktree list`
  is the only lookup that can't drift out of sync with reality. Because every phase branch
  (`feat/<slug>-<suffix>-phase-<n>`) is branched off the outer feature branch, it also contains the
  plan-adding commit, so "branch contains that commit" alone is ambiguous once phase worktrees
  exist — a resumed mid-frontier run could have both the outer flow worktree and still-open phase
  worktrees all matching. After matching candidates by commit containment, filter out any whose
  branch name matches the phase-branch pattern (ends in `-phase-<n>`, i.e. matches
  `-phase-[0-9]+$`) — the outer flow branch never has this suffix. Exactly one candidate must
  remain; if zero or more than one remain after filtering, stop and report the ambiguity rather
  than guessing. Operate inside the path of that one remaining worktree-list entry, rather than
  checking out a branch in the current tree. Keep the fallback for a plan written without going
  through `TRIP-1-plan`'s persist step, updated to create a worktree the same way instead of a bare
  `git checkout -b`.
- Add a new **Phase Scheduling** step, inserted before today's batching section, that replaces
  the implicit "run every phase's batches in one sequential loop" behavior:
  - Parse each phase's `Depends on:` line from the plan.
  - Compute the frontier: phases whose dependencies are all merged into the feature branch
    (initially, every `Depends on: none` phase). **Defensive check**: if the computed frontier is
    empty and unmerged phases remain, stop immediately — do not silently retry or idle — and
    report to the user that the plan's `Depends on:` graph has no root or contains a cycle,
    mirroring how other TRIP loops report a capped/stuck state rather than hanging. This must fire
    on any round, not just the first: a cycle among phases that are *not* the root (e.g. Phase A
    depends on none, Phase B depends on Phase C, Phase C depends on Phase B) lets round 1 dispatch
    and merge A normally, then produces an empty frontier in round 2 with B and C both still
    unmerged — checking "no phase has merged yet" would miss this, so the condition must be
    "unmerged phases remain," not "nothing has merged." (`TRIP-1-plan` Step 3 is expected to catch
    this before the plan is ever approved; this check is the orchestrator's own backstop in case
    that validation was skipped or a plan bypassed `TRIP-1-plan` entirely.)
  - For each frontier phase, dispatch `workspace-worker` to run `git worktree add
    ../<repo>-<slug>-<suffix>-phase-<n> -b feat/<slug>-<suffix>-phase-<n> feat/<slug>-<suffix>` —
    a **flat**, hyphen-joined branch name, **not** `feat/<slug>-<suffix>/phase-<n>`: git refs are
    a path hierarchy under `.git/refs/heads/`, and `feat/<slug>-<suffix>` already exists as a ref
    (a file) once the feature branch is created, so a branch name nested under it is invalid and
    fails with `fatal: cannot lock ref ... exists; cannot create ...`. Branching a
    differently-named branch off a branch that is checked out in another worktree is fine — that
    is the core mechanism this plan relies on (verified empirically); only slash-nesting a new
    branch under the exact name of an existing one collides. Then run one instance of today's
    batch loop (implement → delta batch-review → fix → micro-test-gate → stage) inside it, scoped
    only to that phase's checkboxes. Dispatch one such loop per frontier phase **in parallel** —
    these are independent roles per the routing contract's "dispatch independent roles in
    parallel" rule, just applied at phase granularity for the first time.
  - When a phase's batches are all staged, run a **phase gate**: `batch-reviewer` reviews the
    **full phase diff** (not just the last batch — this is today's "Final pass" step, narrowed
    from feature-wide to phase-wide) plus the testing gate's lint/typecheck/affected-tests,
    scoped to that phase's files. On pass, the phase becomes **merge-ready**.
  - **Merge/cleanup is serialized**, even though implementation and gating stay parallel across
    phases: dispatch `workspace-worker` to commit on the phase branch, `git merge --no-ff` it into
    the feature branch, `git push` the feature branch, remove the phase worktree, and delete the
    phase branch. If more than one phase becomes merge-ready around the same time, dispatch this
    step for one phase at a time, and hold that phase's merge slot — no other phase's merge may be
    dispatched against the feature worktree — from the moment its merge/cleanup step begins until
    that *same* phase's merge is fully resolved and the feature worktree is back to a clean,
    non-mid-merge state, signaled by that phase's own `WORKSPACE_COMPLETE`. A `WORKSPACE_BLOCKED`
    report does **not** release the slot: it surfaces a merge conflict while deliberately leaving
    the feature worktree mid-merge (conflict markers present, merge in progress) so it can be
    resolved in place — see "Merge conflict handling" below. Only the terminal
    `WORKSPACE_COMPLETE` for that same phase, whether from a clean merge or from completing its
    conflict-resolution sub-flow, frees the slot for the next ready phase's merge/cleanup. A single
    working tree/`.git` is not safe for concurrent mutating git operations, so two merges (or a
    merge racing a `git worktree remove`/`git branch -d`) must never run concurrently against the
    shared feature worktree; sibling phases still implementing or gating continue unaffected.
  - **Merge conflict handling**: `git merge --no-ff` leaves a conflict in progress (conflict
    markers in the files, unmerged entries in the index) unless explicitly aborted, so on conflict
    `workspace-worker` must **not** run `git merge --abort` — it reports `WORKSPACE_BLOCKED` with
    the conflicting file list while the merge stays in progress. This is an intermediate status
    within that phase's still-open merge attempt, not a terminal outcome, and the phase's merge
    slot from above stays held throughout. Route an `implementer` scoped only to the conflicting
    files to resolve them directly in the feature-branch worktree, which is mid-merge: the
    implementer edits the conflict-marked files to their correctly resolved content and removes
    the conflict markers (the phase worktree is discarded regardless). Run the normal
    `batch-reviewer` gate over that resolution (the merge's resulting diff). On approval,
    `workspace-worker` runs `git add <resolved files>` then `git commit` — this finishes the
    in-progress merge commit directly; there is no separate "retry the merge" step, since
    committing a resolved merge *is* completing it (a fresh `git merge --no-ff` would only hit the
    same conflict again, as neither branch's history has changed). `workspace-worker` then pushes
    the feature branch, removes the phase worktree, and deletes the phase branch, as in the normal
    case — only after all of that, with the feature worktree fully clean, does it report that
    same phase's `WORKSPACE_COMPLETE` and release the merge slot. Only that phase's slot
    pauses — sibling parallel phases keep running. If conflicts recur on re-review and the
    orchestrator gives up per this plan's "treat it as a `WORKSPACE_BLOCKED`" convention below,
    that stops the entire phase-scheduling loop, not just that one phase: the feature worktree is
    left mid-merge and unsafe for any other phase's merge/cleanup to touch until a human resolves
    it. Record in the flow's running notes (for the eventual PR description and for a future
    planner) that the dependency judgment for this phase pair was wrong, as a lesson for future
    `Depends on:` calls — this is not something to fix retroactively in this plan.
  - Recompute the frontier after each merge; newly-unblocked phases join the next round. Repeat
    until every phase is merged.
- Remove "No commits — history stays clean for release" from Step 5 of the per-batch loop (that
  step still only stages within a phase's worktree); the phase-gate merge above is now the
  commit point. State plainly that the single end-of-implementation commit this plugin used to
  defer entirely to `TRIP-3-release` is now, per phase, a merge commit into the feature branch —
  `TRIP-3-release`'s own final release-docs commit on top is unchanged.
- Re-scope the existing "Final pass" (batch-reviewer full-diff step) out of the per-batch loop —
  it is superseded by the per-phase gate above — and re-scope the Testing Gate and Independent
  Code Review H2 sections to run once, feature-wide, after **all phases** are merged (today they
  already run once after all *batches*; the only change is the trigger, phases instead of
  batches). This is the "exactly one deep review" property from the design: per-phase gates are
  lighter (delta review + testing only), the feature-wide Codex/subagent code review is the only
  pass that sees the whole integrated feature.
- Note in the Handoff-to-Release section that the worktree used throughout this flow persists
  into `TRIP-3-release` (it is the same feature-branch worktree the phase branches merged into).

### 7. `plugins/codex-bridge/skills/codex-code-review/prompts/start.tpl`

**File**: `plugins/codex-bridge/skills/codex-code-review/prompts/start.tpl`

**Current state**: Lines 8-12 run `git diff HEAD` unconditionally, with a fallback to `git diff
@{u}...HEAD` or `git log --reverse main..HEAD` that only fires when `git diff HEAD` returns
nothing. Once phases commit progressively, `git diff HEAD` is non-empty after the first phase
commit — scoped to only the most recent commit — so the fallback never fires and the reviewer
silently reviews a fraction of the real change.

**Modifications**: Replace the `git diff HEAD` / conditional-fallback block unconditionally with
an instruction to resolve the project's main branch name from `docs/TRIP.md` § Project and run
`git diff $(git merge-base <main branch> HEAD)` — a single-ref diff against the merge-base
*commit*, not a triple-dot (`A...B`) diff. This distinction is load-bearing: `git diff A...B` is
always a commit-to-commit comparison (it is defined as `git diff $(git merge-base A B) B`), so
with `B=HEAD` it would silently exclude the working tree exactly like the bug it's meant to fix —
`TRIP-2-implement`'s Independent Code Review resume loop has `fixer` edit files and immediately
resume `codex-code-review` with no commit step in between, so the diff command must see
uncommitted state or the reviewer approves without seeing most of it. `git diff <commit>`
(single-ref form) diffs that commit against the current working tree/index, so it correctly
captures both every commit made since the branch diverged *and* any currently uncommitted edits.
`docs/TRIP.md` is **not** currently in this prompt's "Prerequisites — read first" list (only
sibling templates — `codex-batch-review`, `codex-release`, `codex-release-verify`, `codex-test` —
already read it); add it as a new item to that list here rather than asserting it's already
covered. No new template placeholder or `codex-run.py` change is needed beyond that: the
main-branch name is resolved by Codex itself at review time from a doc it will now read, the same
way it already reads `docs/archi/index.md` and `checklist.md`.

## Technical Considerations

- **Pattern usage**: follow the existing role/harness/completion-tag contract in
  `plugins/trip/references/agent-routing.md` throughout — worktrees and phase parallelism are
  additive to that contract (new authorized operations, new "independent roles" instance), not a
  replacement for it. No wiki page documents worktrees yet (confirmed absence, not drift); flag
  this plan's own to-do to run `/wiki-ingest` after landing.
- **cwd threading is the load-bearing mechanic**: none of today's TRIP skills carry an explicit
  "operate in this directory" concept — they assume the repo root. Every SKILL.md touched by this
  plan must say explicitly, in its own words, that downstream dispatches carry the worktree path
  forward; leaving this implicit is exactly how a future editor reintroduces the single-tree
  assumption by accident. One deliberate exception exists: `TRIP-3-release` Step 11 switches cwd
  back to the primary tree to remove the now-merged worktree (see that section's "Flag this
  explicitly, not parenthetically" note above) — it is the one place this rule reverses, called
  out there so it isn't mistaken for a violation of this rule.
- **Collision-safe naming**: the short suffix (hash or timestamp) is computed once per outer flow
  and reused for every phase worktree and phase branch spawned inside it — worktree directory
  `...-<suffix>-phase-<n>` and branch `feat/<slug>-<suffix>-phase-<n>`, both flat and
  hyphen-joined, never slash-nested under the feature branch name (see the Phase Scheduling step
  above for why nesting is an invalid git ref) — so phase worktrees/branches inherit collision
  safety from the outer suffix rather than needing their own.
- **Lesson for future dependency-graph calls**: when `TRIP-2-implement`'s merge-conflict handling
  fires, it means a planner judged two phases independent (`Depends on: none` each, or no edge
  between them) and was wrong. This plan's own `Depends on:` calls below are a real instance of
  the same judgment call this feature asks future planners to make — record any such correction
  discovered during this plan's own implementation back into this file's phase headings rather
  than silently fixing it forward, since that is the exact feedback loop point 5 of the design
  asks every future plan to close.
- **Do not touch `codex-batch-review`**: its delta review is deliberately scoped to uncommitted
  changes only (`git status -s && git diff`, prepared by `workspace-worker` and handed to it as
  raw input — the `review.tpl` itself contains no hardcoded `git diff` invocation to fix). That
  scoping is correct and unrelated to the `codex-code-review` bug; leave it exactly as is.
- **No `EnterWorktree`/`ExitWorktree`/Agent Teams**: those are Claude-Code-only mechanisms; TRIP
  workers must remain dispatchable to other harnesses (e.g. Cursor) that lack them. All worktree
  lifecycle goes through plain `git worktree`/`git merge` commands inside `workspace-worker`'s
  existing allowlist mechanism.
- **Edge cases**: a flow with a single phase (`Depends on: none`, no siblings) degenerates to
  today's behavior exactly — one phase worktree, one merge, one feature-wide review — so small
  plans pay no new ceremony. A plan with all phases mutually independent maximizes parallelism (a
  full frontier on round one). A merge-conflict retry that itself conflicts again is not
  explicitly bounded by this plan — treat it as a `WORKSPACE_BLOCKED` the orchestrator surfaces to
  the user rather than retrying indefinitely, consistent with the existing 5-round caps elsewhere
  in TRIP's review loops.
