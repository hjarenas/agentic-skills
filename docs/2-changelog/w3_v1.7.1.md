## Changes

- **`trip` plugin (1.7.0 → 1.7.1)**: a patch fixing a defect shipped in 1.7.0. That release added
  two standalone migrations to `TRIP-upgrade` — the worktree-bootstrap profile subsection and the
  `git worktree` permission allowlist — and both sections claimed to run "on every upgrade path",
  but nothing in the skill implemented that. They were unreachable for exactly the projects that
  needed them, via two independent traps:
  - Phase 0's path table carried a row reading "already has `## Agent routing` and no legacy
    skills → report 'already current' and stop without edits". Every project already on 1.5.0 or
    1.6.0 matches that row, so the upgrade ended before either new migration was considered.
  - The **Profile-only routing migration** ends with "skip Phases 1-6", and both new sections sat
    after it in the file, so that path skipped them too.

  Confirmed against a real downstream project (`crm`): it has `## Agent routing`, no legacy skills,
  and no git allowlist — it needed the allowlist migration and had no way to reach it.
- **The fix — Phase 0 now makes two independent decisions.** A **structural path** (one of four
  table rows) and a set of **standalone migrations**, each run whenever its own condition holds, on
  the legacy, routing and "no structural work" paths alike. The "already current" no-op exit
  survives, but now requires both standalone conditions to be satisfied as well, so it means what
  it says. The routing migration hands off to the standalone migrations before skipping Phases 1-6,
  and Phase 6 gained the same hand-off for the legacy path. The frontmatter `description` now names
  both migrations, which is what makes them discoverable in the first place.
- **A Major regression the fix itself introduced, caught by review.** The first attempt said the
  standalone migrations run on *every* structural path, which contradicts the "Neither exists →
  point at `/TRIP-init` and stop" row. The sharper problem was that both migration conditions hold
  **vacuously** on an uninitialized project: a nonexistent `docs/TRIP.md` trivially "has no"
  bootstrap subsection, and the allowlist condition never mentioned `docs/TRIP.md` at all. An agent
  could have written a git permission allowlist into `.claude/settings.json` of a repository TRIP
  was never initialized in. It is closed **redundantly** — an explicit carve-out in Phase 0 *and* a
  precondition inside each migration — so removing either guard does not reopen it.
- **Probe/condition mismatch.** Phase 0's inspection grepped for `git worktree add` while the
  migration's condition is the `Bash(git worktree add:*)` entry under `permissions.allow`. A
  project carrying that command as a `deny` or `ask` entry would have matched the probe and
  silently skipped a migration it still needed. Probe and condition now match.
- **Files Reviewed is now derived, not recalled (`TRIP-3-release`).** A second, late change in the
  same patch: Step 3.3 now says where a code review's **Files Reviewed** list comes from — derive
  it from the real change set by reconciling `git status --short` against
  `git diff --cached --name-only`, count the paths, confirm all are listed, note that the set
  covers release artifacts as well as feature files (the CR is written before the release commit
  exists), and record which subset each review round re-examined. Step 3.5's verification line
  gained a matching Files-Reviewed completeness check alongside its placeholder, sentinel and
  version checks. The list has come up short in **three consecutive releases** — corrected after
  1.6.0 in `af1f8cb`, again during 1.7.0, and again in this release's own verification — because
  Step 3 never named a source, so every worker listed only the file it had been told about. Same
  spirit as the release itself: move a repeated hand-correction into the framework. Still a patch —
  no new capability, a defect fix to release bookkeeping.
